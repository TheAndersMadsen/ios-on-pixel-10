# M2: the firmware's own state from shared memory, and a stock-shaped health check (2026-11-03)

Labels: **physical** = phone log; **source** = code or vendor header read; **host** = built or run on m1box/Mac;
**inference** = not tested. No phone, adb, fastboot or QEMU action was taken for this document. Built, **not booted**.

## 0. Result in one paragraph

Source comparison with the pinned vendor driver (GrapheneOS `google-modules/powervr` @5940a317, lga production config) shows
that most of what rung 5 counted as symptoms is stock behaviour on this configuration, and that rung 5's own pass criterion is
not stock's. `RGX_NUM_DRIVERS_SUPPORTED` is 1 (native, no AutoVz), so stock never reads the firmware connection state or the
OSINIT compatibility block. It never sends an OS-online command, and it never waits on a return slot for `HEALTH_CHECK`. The doorbell
and the memory model match stock. Rung 6 (`blazer_gpu_tipc=6`, kernel `kernel.gpu-m2-r1`, image `a7-ios-system-gpu2`) is the fix
and M2's decode in one boot. It turns on the firmware's own trace log. It prints the firmware's view (OS runtime flags, CR poll, fault and
assert buffers, FWCCB) before any kick. It then sends the commands the way stock does: `HEALTH_CHECK` needs only to be consumed,
and `STATEFLAGS_CTRL` with no flag change is the first command whose return slot stock waits on. Health PASS is `CMD_EXECUTED` on
that command. After the commands it prints the view again, the raw firmware log, and the 18 M1 registers. The DEBUG_DUMP
FWCCB message is still unexplained by source. Rung 6 shows whether it arrives at boot or only after our command.

## 2. Our init sequence against stock's (source)

| Step | Stock (file:line at the pin) | Ours, rung 5 | Rung 6 |
| --- | --- | --- | --- |
| Shared data | `RGXSetupFwOsData`, `RGXSetupFwSysData` (`rgxfwutils.c` 2125-2830, 2857-3000) | same structures, bottom of the main heap; config flags, sRegCfg, sig buffers, timer arrays, OPP left zero (`blazer_gpu_tipc.c:240`) | same, plus the trace buffer (below) |
| Trace log | log type from apphint (production `PVRSRV_APPHINT_ENABLELOGGROUP RGXFWIF_LOG_TYPE_NONE`); buffer allocated only when a type is set (`RGXTraceBufferInitOnDemandResources`, `rgxfwutils.c:1418-1490`) | type 0, no buffer | type `0xc62f` (TRACE + MAIN MTS CLEANUP BIF POW HWR MISC VZ), one 12000-word buffer (`RGXFW_TRACE_BUF_DEFAULT_SIZE_IN_DWORDS`), written before START |
| Image | `SEND_FIRMWARE_IMAGE` before the first power-on (`gpu_secure.c` 690-780) | same, result 0 (physical) | same |
| Start | `_RGXDoStart` -> `pfnTDRGXStart` = `gpu_secure_start` = SMC `0xC300000C`/1 (`rgxpower.c:1156-1190`, `gpu_secure.c:333-363`) | same, `-> 0x0` (physical) | same |
| Wait | poll `bFirmwareStarted` only (`rgxpower.c:1341-1370`) | same, then 3 s on `eConnectionFwState` == ACTIVE (rung 4) | `bFirmwareStarted` only |
| FW connection | native: `KM_GET_FW_CONNECTION` is the constant `RGXFW_CONNECTION_FW_ACTIVE` and `KM_SET_OS_CONNECTION` is empty (`rgxfwutils.h:1520-1528`, `RGX_NUM_DRIVERS_SUPPORTED 1` in `pixel/lga/production/config_kernel.h:29`) | reads shared `fw 0 / os 1` as a fault | not used |
| Compat checks | native: from the FW info header, not `sRGXCompChecks` (`volcanic/rgxinit.c:1450-1570`, `rgxfwutils.c:3012`: OSINIT checks only for GUEST) | reads `comp.updated 0` as a fault | printed by the existing DIAG, not judged |
| OS online | `RGXFWSetFwOsState(ONLINE)` only from the VZ paths (`vmm_pvz_server.c:123`, `vz_vmm_vm.c:123`); native only sends OFFLINE at power-off (`rgxpower.c:830`) | never sent | never sent (stock doesn't) |
| Command | `RGXSendCommandRaw`: reset the return slot **only if the caller will wait**, copy, write offset, `RGX_CR_MTS_SCHEDULE` (0xb00) = DM_GP 0 (`RGXSendCommandRaw`, `rgxfwutils.c:3999-4210`; `__MTSScheduleWrite` 230) | same doorbell; the firmware read the command (physical), so the doorbell works | same doorbell (disassembly: `str wzr, [x20, #0xb00]`, `receipts/gta_kccb.dis.txt`) |
| Pre-kick | `_SendPreKickCacheCommand` sends an MMU cache command only if invalidations are pending (`rgxfwutils.c:4965-5050`). None are pending before any mapping (inference) | none | none |
| Health check | `RGXFWHealthCheckCmd`: return slot **NULL**, waits on nothing (`rgxfwutils.c:6100-6112`) | requires `CMD_EXECUTED` within 1 s, so FAIL | consumption only, return value printed |
| Execution proof | first waited command, e.g. `RGXStateFlagCtrl`: `STATEFLAGS_CTRL` + `RGXWaitForKCCBSlotUpdate` (`rgxfwutils.c:5636-5720`; the kernel source comment calls it RGXFWSetFwConfigFlags) | none | `STATEFLAGS_CTRL` (0x2abc00ce), no flag change (sysdata `ui32ConfigFlags` stays 0), waits ≤1 s for `CMD_EXECUTED` |
| Cache maintenance | `RGXFwSharedMemCacheOp*` for cached CPU maps | carve-out mapped as device memory; FW pointers in the uncached region `0x4xxxxxxx` | same |
| FWCCB DEBUG_DUMP | host handler only schedules its own debug dump (`rgxfwutils.c:5344-5356`); no reply to the firmware | read-only capture | captured before the kick, after HEALTH and after STATEFLAGS; never acked |

What this means (inference): the candidates the task named are ruled out by source: a missing OS-online command (native never
sends one), the doorbell register (identical, and it is consumed) and cache flushes (uncached device mapping). The remaining
known difference that can stop health is the pass criterion. Unknowns that rung 6 measures: whether the firmware executes any
command, and the cause of DEBUG_DUMP (firmware assert, a CR poll on a register we never set up, our OS seen as offline in
`aui32OsRuntimeFlagsMirror[0]`, or a firmware fault). The TA's `24.2 vs 26.1` line is consistent with stock: the stock
`gpu_secure.c` itself carries a "Hack for 26.1 RISCV FW" against a TA built for 24.2 (`gpu_secure.c:763`). Its `process_st_info`
error 278 is still unresolved (no Android comparison yet, PLAN §5).

## 3. What rung 6 reads (offsets: host-measured from the pinned headers)

test checks this agreement.

| TRACEBUF type, ptr, wrap, buffer address, size, flags | +0x0, +0x8, +0xc, +0x10, +0x1b0, +0x1b4 | `trace type … size … ptr … wrap …` |

| Firmware log | trace buffer, ≤4096 words | `M2 TB oooo: 8 words`, decoded on the host by `m2/tools/fwlog_decode.py` against `rgx_fwif_sf.h` (`KCCB Slot %u: Cmd=…`, `Unknown KCCB Command`, `Invalid KCCB cmd`, driver state transitions, power, HWR) |

Writes in rung 6 beyond rung 4's: the trace control fields, return slots 0 and 1, KCCB slots 0 and 1, the write offset, two MTS
kicks. It never writes the FWCCB read offset or acks anything. It sends no second command after one the firmware has not read.

### Pass criteria

1. **Health PASS:** `M2 STATEFLAGS_CTRL: slot 1 read … return 0x1`, then `M2 HEALTH PASS`, then `rung 6 PASS, boot ended on purpose`.
2. Decode complete: three `M2 <when>:` groups (boot, after-health, after-stateflags or stateflags-fail), `M2 fwlog: end`,
   `survey done, 18 registers` with no MMU fault bit and `CLOCK_RUNS`.
3. The only panic is the rung's own; fastboot is back, and the return check PASSes.

Results that are findings, not failures of the boot (each points to M3):

| Seen | Meaning | M3 next |
| --- | --- | --- |
| PASS, `trace ptr > 0` | the firmware executes commands; rung 5 failed on its criterion | `docs/NATIVE-METAL.md` next rung: memory context registration over the KCCB |
| `M2 HEALTH FAIL … STATEFLAGS_CTRL read, not executed` + `assert0 line N` | the firmware asserted | fix what the assert's file:line names |
| … + `cr poll addr 0x… count >0` | the firmware is stuck polling a register | power or set up that block (the address names it) |
| … + `os0 … state OFFLINE` | the firmware sees our OS offline | look for the driver-state lines in fwlog (`fw state transition`, `CCB init status`); in native stock sends nothing for this, so the cause is in our OSINIT |
| `fw_faults > 0` | firmware fault, file:line printed | as for the assert |
| DEBUG_DUMP already in `M2 boot` | raised at firmware init, not by our command | the fwlog entries before it |
| `HEALTH_CHECK: slot 0 NOT READ` | the firmware no longer reads the KCCB (the trace log changed something) | repeat once without the log (rung 5) |
| `trace … ptr 0` | the firmware writes no log: it ignores the log type, or the buffer is not mapped for it | read the other lines; the log is optional |

Stop and do not repeat: any panic other than the rung's, an SError during the survey, no fastboot after the reset, or a failed
return check. Rollback: the PSCI reset goes back to fastboot, and nothing is written to the phone.
