## 1. Kernel changes (SRC, `b2/xnu-src/0001-hk-bt-b2.patch`, candidate files + baseline from cc42295)

1. **Gate (`blazer_bt_gate.c/.h`): Broadcom vendor allow-list, all at level 0, parameters checked.**
   `0xfc01` Write BD_ADDR (exactly 6 B) · `0xfc18` Update UART Baud (only `00 00` + le32 4,000,000, the rate the kernel already
   set) · `0xfc27` Write Sleep Mode (only mode 0: no LPM, nothing drives dev/host wake) · `0xfc6e` Read Controller Features and
   `0xfc79` Read Verbose Config (no parameters). Every other vendor opcode (firmware 0xfc2e/0xfc4c/0xfc4e, UART clock 0xfc45,
   Apple's own set) stays local: Unknown HCI Command, never on the UART. A listed opcode with other parameters: Command Disallowed
   (new counter `BG_WHY_VPARAM`). Standard table and `blazer_bt_tx` levels unchanged. `bu_serve` re-checks every packet with the same
   `bg_check`, so the UART thread enforces the list too.
2. **Bridge starts when the chip serves (`blazer_btuart.c`, `blazer_btuart_hw.[ch]`).** Before, the kernel control and nexus were
   registered 1 s into the boot; on the phone the chip is served only after Wi-Fi firmware + ~70 s of 115200-baud BT firmware,
   and a bluetoothd that connected, timed out and closed would have ended the one-per-boot session first. Now `bu_link.ready`
   calls `blazer_bt_bridge_start` at the top of `bu_serve` (after firmware, 4 Mbaud, RTS/CTS). Serve bound stays 120 s.
3. **Bounded flow log (`blazer_bt_bridge.c`):** first 64 lines of `to chip 0x%04x`, `from chip: complete 0x%04x status 0x%02x`,
   `from chip: status …`, `from chip: event …`; opcodes and statuses only, no parameters or addresses. Summary gains command,
   complete and status counts.
4. **QEMU-only fake controller** `blazer_bt_qfake=N` (1..600 s): no register/PMIC/SMC/pad access, no Wi-Fi wait; after N s it
   answers what the gate passes (version = the BCM4390B1's post-firmware answer, placeholder address) for 120 s. The phone's
   token list never admits it.

Evidence: `receipts/gate-host-test.txt` (ASan/UBSan, 16,909 checks PASS incl. all 1024 vendor OCFs × 4 levels × 4 parameter
shapes; baseline fails 170; 4 mutations caught: baud unchecked, sleep unchecked, all vendor sent, firmware opcode listed).
`receipts/kernel-bt2-objects.txt`: `_vendor_ok` disassembly compares 0xfc01/0xfc18/0xfc27/0xfc6e/0xfc79 and 0x900 (4,000,000 low
half), `_bridge_ready`, `_qf_answers`, `_boot_qfake`, the new strings. Build: `xnu-src/build_bt2.py` (kernel-build-slot lock,
refuses a dirty tree or changed baseline), log `receipts/build-bt2.out`: `hk-bt-b2` 9aa76a93 built rc 0, tree restored to **p1**
(b228c4f) and p1 rebuilt rc 0. (Afterwards another owner switched the Mac tree to `hk-screen-dbg5`; not this agent.)
`kernel.bt2` 4cf8224f75767c6f65510de77bf5a8287a897703f234c0fbe5eb9297ef84eb6e, unstripped 55123833fc758c4b9025d5e416a3c63b372aa4b0f0a397949f46b0cce26454be.

**Why nothing reaches the transport (static, bluetoothd r3):** the chip path is LocalDevice's
`Beginning asynchronous power init` (fn 0x100580fec, vtable 0x100aea150) → default power (`com.apple.BTServer`
`defaultPoweredState`, ON when absent) → `ChipBoot` (fn 0x100581df4: VM check, BlueTool `boot`, "Unknown platform/chipset…") →
`Beginning asynchronous power on`. None of these log lines appears in any run: **power init is never called** in QEMU. What calls
it is not found yet (virtual, no RTTI; candidates: a BTServer client session, the first-unlock/Buddy state, the WirelessRadioManager
check-in — `com.apple.WirelessRadioManager` is in the overlay's disabled set and bluetoothd logs `PurpleCoexManager XPC connection
error`). Note also bluetoothd skips chip init "inside a Virtual Machine" (vtable+0x118 check), so QEMU may never be able to show
the HCI exchange even once power init runs. Tools: `tools/xref.py`, `tools/fnstrs.py`.

`BT_DEVICE_ADDRESS` env is an alternative bluetoothd reads for the address (`could not find BT_DEVICE_ADDRESS env variable`);
the nub also supplies transport-encoding 7, so the phone image uses the nub.

### Attended boot (owner; bare `fastboot boot`, then the return check)

`tools/bootios research/images/a7-ios-system-bt2/boot.img a7-ios-system-bt2 --mach research/ios26-connectivity-r1/bluetooth/b2/build/kernel.bt2.unstripped --wait 480`

Owner: wait for Home, then open **Settings > Bluetooth** (likely the client that asks bluetoothd for power; see 3) and say whether a
toggle / "Bluetooth" row is shown and its state. Nothing else is needed.

Expected kernel-log lines, in order (decode with `tools/all_decode.py … research/images/a7-ios-system-bt2/manifest.json`):
1. `hk_env: bluetoothd gets BT_HCI_TRANSPORT=H4:POSIX`, `hk_env: bluetoothd gets BT_CHIP=ACI BT`, `exec bluetoothd`; **no**
   `hk_deny: bluetoothd refused`; `hk_deny: Spotlight refused` as in r10.
2. `blazer-wifi: … GO: firmware up, doorbell …`, then `blazer-bt: Wi-Fi firmware up, N s. Starts`.
3. As bt-stream-r1: `GO: HCI Reset answered`, `firmware file: 824184 bytes, 3199 records`, `Launch RAM answered`,
   `GO: HCI Reset after firmware`, `local name: BCM4390B1 …`, `GO: 4000000 with RTS/CTS, Reset and Version answered`.
4. `btsk: the Bluetooth UART's nexus: <UUID> (error 0)`, `blazer-bt-bridge: kernel control registered (0), gate level 0: nothing that
   transmits passes`, `blazer-bt: serve: the UART is bluetoothd's now, gate level 0`.
5. **B3 pass lines:** `blazer-bt-bridge: bluetoothd connected (unit N), chip serving`, `btsk: bluetoothd opens a channel …`,
   `btsk: the channel is connected: the H4 stream runs through it`, `blazer-bt-bridge: to chip 0x0c03`,
   `blazer-bt-bridge: from chip: complete 0x0c03 status 0x00`, `to chip 0x1001`, `from chip: complete 0x1001 status 0x00`;
   any `held 0x…` lines name the vendor/unsupported opcodes bluetoothd wanted (the input for the next allow-list review).
6. `blazer-bt: serve: ends, … lsr errors 0x…`, the bridge summary (`from bluetoothd N packets (M commands to the chip) …`),
   `stopped; endpoint offline (ENXIO)`, `tidy: done` ~120 s after line 4.
7. launchd: one `com.apple.bluetoothd` spawn, no `exited due to exit(1)` / respawn loop before the serve ends; HK TOP shows
   one bluetoothd pid; launchd/audiomxd stay quiet (0 or few `BTAudioHALPlugin` lookups).

Read-out: if 4 appears and 5 does not, bluetoothd never opened the transport on the phone either (same as QEMU: power init not
triggered) — the next step is finding power init's caller (section 3), not the kernel. If 5 shows `held` vendor opcodes and
bluetoothd then stops, review those opcodes for the list. Stop: a panic other than the 300 s deadline, Home lost, a bluetoothd or
audiomxd storm, any `serve-gate` stop (`BU_STOP_SERVE_GATE`), UART lsr errors with lost packets.
Rollback: deadline/PSCI reset to fastboot, `return-check.sh`; nothing persists (root read-only, `/private/var` in RAM).
The chip's radio: level 0 passes nothing that transmits; BT firmware download and Reset are what bt-stream-r1 already did.
