# fb120: 120 Hz by fast copy, plus an optional LTPO idle drop (2026-11-03, HOST + Mac build + QEMU; not booted on the phone)

Labels: **M** = measured in a named phone log, **S** = source, **H** = host test, **Q** = QEMU (TCG, no Tensor DPU), **I** = inference.

## 1. Why every boot ran at 60

- The panel's TE already runs at **~120.6 Hz** (M, phone-fast-r2: TE every 8291 µs; int2 `frame_us` ~9.1 ms). In command mode the
  panel keeps its own frame. "60 Hz" was only a kernel policy.
- `sweet_fb_refresh_decide()` (S, hk-int1 `sweet_fb_refresh.h`) gives 120 only with zero-copy flip. Flip has never passed on the phone,
  so `hk_fb_refresh=120` ran as 60. At 60 the kernel publishes no `IOMFBDisplayRefresh/displayMinRefreshInterval`, so CoreAnimation keeps its
  literal 1/60 heartbeat (S, QuartzCore 23G90, static).
- That policy dates from a ~5 ms copy. With `hk_fb_fast=1` (on the int1 line) the whole 11.3 MB copy takes **1.5-2.1 ms** (M, A7 r3,
  `display/PLAN.md` §2.2). A TE leaves 8291 − 5370 = **2.9 ms** free after the transfer, so the copy fits.
- Measured today (M, live int1/int2 logs): at most **39.9 swaps/s = kicks/s**, `max_gap_us` ~32,000 with small damage rects. The kernel
  kicks as soon as the last fetch lands. The ~40/s is CA's 60 Hz ticks beating against completion, and a missed tick costs 16.7 ms.
  Inference: at 120, a missed tick costs 8.3 ms.

## 2. Change (XNU `hk-fb120` = **cd60b8d**, one commit on hk-int1 484717f; `0001-hk-fb120.patch`)

- `sweet_fb_refresh_decide(asked, flip, fast_copy)`: 120 runs with flip **or** `hk_fb_fast=1`. Without either it still falls to 60.
  When 120 runs, the kernel publishes `displayMinRefreshInterval = 2^32/120` (this code is unchanged; it was unreachable without flip).
- While a frame waits at 120, the FRM_DONE poll runs every **250-500 µs** (was ≥ 1000). Worst case is 5370 + 500 + 2100 µs, which is
  under 8291 (H). Polling without a waiting frame, at 60, and with refresh off is identical to int1 (H, compared exhaustively).
- **Same token, same bytes:** `hk_fb_refresh=121` / `122` = 120 busy **plus the LTPO idle drop** to 30 / 10 Hz. They reuse the existing
  hk_dpu VRR machine (`sweet_idle_vrr.h`: 1.5 s idle → DCS 0x83 rate, the next swap restores 120 before its kick, any DCS failure ends
  VRR for the boot). They also imply `hk_fb_fence=1` (completion quarantine), set in `sweet_scanout_attach` before the first kick. No hk_dpu
  or hk_fb_fence token is needed.
- New log lines: `SWEET FB: refresh 120 by copy: fast 1, waiting poll 250-500 us` and `tensor-dpu: fence on for hk_fb_refresh 12x`.
- Zero-copy flip, dirty copy and hk_dpu bits are untouched and stay off. Not on the line: `hk_fb_dirty` (never booted).

Panel/DT: the FDT names the panel `google,gs-bzea` on `gs-dsi0-connector`, with a `vddd-lp-microvolt` low-power rail. It holds no mode
timings (they live in the panel driver). The rate DCS table is the existing `tdpu_panel_rate` (0x83: 0/1/2/3 = 120/60/30/10). It is
compiled but has never run on the phone (`hk_panel_hz`, NOTES-full).

## 3. Host test (`test/test_fb120.c`, ASan+UBSan, `-Werror`): **PASS, 18,315 checks** (`test/test_fb120.out`)

Covers decide/vrr/fence for 0..999, unchanged old answers, VRR init/step for 121/122, poll bounds, and a TE timeline model. The model is
kernel side only, with a producer that always has a frame waiting. int1's 60 policy already reaches ~120 kicks/s in the ideal case. The new
poll holds 120.2-120.7 where int1 drops to 89-101 (copy 2.1 ms, 200-500 µs wakeup jitter). **So the decisive change is CA being told 120;
the poll adds margin.**

## 7. Phone test (coordinator; owner present; bare `fastboot boot`, return check after)

```
tools/bootios research/images/a7-ios-system-fb120/boot.img a7-ios-system-fb120 \
  --mach research/ios26-phaseb-r1/display/fb120/build/kernel.fb120.unstripped --wait 1080
# then research/ios26-dualboot-r8/return-check.sh research/ios26-dualboot-r8/attempts/a7-fb120-after-boot
```

Owner, after Home: open Settings and fling the list up and down continuously for ~20 s, then go back Home. Swipe between the Home page
and the Today view for ~10 s. Then leave it idle for 30 s.

Pass (kernel log, first copy of the boot):
1. `SWEET FB: refresh asked 120, running 120, flip 0, interval 35791394` and `SWEET FB: refresh 120 by copy: fast 1, waiting poll 250-500 us`.
2. **120 Hz shown:** at least one `SWEET FB: rate swaps N/s kicks N/s` with **kicks > 60.0/s** during the scroll (int1/int2 max: 39.9).
   Kicks above 60.3/s are impossible at one frame per two TEs, so they prove frames on consecutive TEs.
3. No regression: `tensor-dpu: frames … refusal 0`, no `kick failed`/`latched`/`no FRM_DONE`, underruns not above int1's rate, Home as int1,
   no panic. The owner sees no tearing or stale tiles.

Reading a fail: `running 120` with kicks ≤ 60 means the kernel did its part and CoreAnimation stayed at 60 (I: the identity is D421AP/
iPhone12,3, a 60 Hz model, so QuartzCore may cap there; or the frames cost more than 8.3 ms of CPU). The next step is then the CA/identity side,
not the DPU. Rollback: int1 (the same line with `hk_fb_refresh=60`).

**Second boot, only after fb120 passes:** the same command with `a7-ios-system-fb120v` (`hk_fb_refresh=121`). Extra pass lines: `tensor-dpu: fence on
for hk_fb_refresh 121`, `SWEET FB: vrr high 120 low 30 idle_us 1500000`, then during the 30 s idle `SWEET FB: vrr low 30 Hz rc 0 lows 1 …`, and on the
next touch `SWEET FB: vrr high 120 Hz rc 0 …`. Stop on any `rc` ≠ 0 (`off for this boot`), `fence quarantined`, or a frozen screen. A DCS rate change
has never run on this panel.
